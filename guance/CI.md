# Headless Shell CI

The workflow validates the build scripts on every push. A manual run selects Linux amd64, arm64, or both, in `dev`, `release` or experimental `release-size` mode. Pushing a tag named `build-dev-*` also starts an amd64 `dev` build on the standard runner; ordinary pushes never start a build. No pull request event runs this workflow.

`dev` disables PGO, ThinLTO and the dependent CFI hardening for faster iteration; its artifact is labeled `dev` and is only for development verification. `release` retains the upstream PGO and ThinLTO settings. Linux amd64 enables upstream CFI by default, whereas Linux arm64 does not; the builds therefore do not have identical CFI protections. Both retain the CDP screenshot capability. A successful build uploads a tarball, `SHA256SUMS`, and `build-info.json` as a workflow artifact; it does not publish a GitHub release.

Both architectures build on an x64 host; arm64 uses Chromium's pinned sysroot and cross toolchain. The ARM build output is explicitly labeled `unverified` until a separate native `ubuntu-22.04-arm` job passes the CDP screenshot smoke test. Only its `verified` artifact contains a passed ARM smoke report. ARM cross compilation and native verification have not yet completed an end-to-end run.

`release-size` adds `optimize_for_size=true` to the optimized lean configuration without intentionally removing Web APIs. On amd64 it has passed GN configuration checks with PGO, ThinLTO and CFI enabled, but has not yet completed a full build or a runtime comparison. Compare summed process PSS, private/shared pages, startup and screenshot latency, and functional smoke results with `release`; binary or archive size alone does not establish a memory benefit. It writes to `src/out/Guance-release-size` and never replaces the normal release output.

For a manual run, select the desired branch and mode, an existing Linux x64 runner label, and a positive job count. GitHub only exposes `workflow_dispatch` when the workflow file exists on the repository's default branch. Before that, pushing a `build-dev-*` tag pointing to the desired commit can start a development build; manual release builds require the workflow on the default branch. Tags should be created only by authorized maintainers.

The default is `ubuntu-22.04` with four build jobs. GitHub's standard public Linux runner has 4 vCPUs, 16 GB RAM and 14 GB storage; the workflow checks for at least 50 GiB free before downloading sources. This starting threshold is based on local observations, not a guarantee against running out of space. The push validation reports disk, memory and CPU resources without starting a build. A standard runner may fail the check, and a cold build may exceed the six-hour hosted job limit. The workflow does not remove preinstalled runner software. No first-build time is promised. Inspect the resource and build logs before selecting a larger existing runner. GitHub's larger Linux runners include an 8-vCPU, 32-GB RAM, 300-GB option; these may incur charges and must already be configured by an administrator.

A trusted, dedicated self-hosted Linux x64 runner with sufficient SSD space and memory can preserve its build directory between runs. Set the repository variable `HEADLESS_BUILD_ROOT` to an absolute directory on that runner, and provide its configured label when manually dispatching. The workflow creates separate `amd64` and `arm64` subdirectories; existing builds directly in the root are not reused. Without the variable, the runner's temporary directory is used. The workflow does not clean the self-hosted machine. The preflight requires 50 GiB currently free even for an incremental build; adjust capacity if it fails. Restrict access to the runner and run only trusted commits, since a workflow can execute repository code on that machine. Do not attach this runner to public pull-request workflows.

GitHub-hosted runners install Chromium's Linux build dependencies and the `fonts-noto-cjk` and `fonts-liberation` packages after preparing the source. Self-hosted runners must have these dependencies installed beforehand; the workflow does not run sudo on them.

The source archive and its verified digest are fixed by `prepare.sh`. If available, aria2 downloads the archive with eight connections; otherwise curl is used with connection, transfer and stall limits. The official Ubuntu 22.04 runner image includes aria2. Source preparation has a 45-minute step limit. Preparation overlays changes from the pinned Chromium baseline through the selected fork commit. Build outputs are isolated by mode under `src/out/Guance-dev`, `src/out/Guance-release` and `src/out/Guance-release-size`. A persistent output directory can accelerate repeated builds; it does not make the first build faster. Compiler and ThinLTO caches cover different work, and any cache benefit should be measured. GitHub Actions cache defaults to 10 GB per repository and entries unused for seven days are removed, so the workflow does not upload the whole build tree to Actions cache.
